## 1. 产品概述

### 1.1 产品定位

记忆大师是一款面向知识工作者的 AI 工作记忆产品。

它的核心目标不是做传统知识库，而是帮助用户将日常工作中的碎片信息、经验、判断和阶段性结论沉淀为可复用的记忆卡，并在下一次工作中自动或手动调用这些记忆，为用户提供更贴合上下文的建议，以推动工作推进和辅助决策。

### 1.2 产品目标

围绕用户真实工作链路，建立一条可持续复用的闭环：

1. 用户在日常工作中产生大量分散信息，如会议结论、聊天反馈、需求取舍、阶段性判断、网页资料和手动记录内容。
2. 系统将这些信息整理为结构化记忆卡，优先支持用户手动添加，并支持对话后手动沉淀为记忆卡。
3. 用户在下一次遇到问题时，系统自动召回相关记忆卡，用户也可以手动指定记忆卡参与本次回答。
4. AI 基于当前问题与相关记忆卡生成更有上下文的建议，帮助用户推进工作和辅助决策。
5. 用户可将本轮新的有效结论再次沉淀为记忆卡，形成持续增强的工作记忆体系。

### 1.3 目标用户

当前 1.0 版本优先面向高频决策型知识工作者，首要目标用户为产品经理。

典型特征如下：

- 每天在多个会议、聊天、文档和需求之间频繁切换。
- 经常需要复盘历史结论、向不同角色解释背景。
- 信息记录很多，但难以在后续工作里快速调用。
- 在需求评审、版本规划、复盘沉淀、客户反馈分析等场景中，对历史判断复用有强需求。

### 1.4 用户核心痛点

1. 背景重复解释成本高。
2. 历史判断难以复用。
3. 信息有记录但没有转化为可调用的工作资产。
4. 不同时间和场景之间的工作思考缺少连续性。
5. 当前工具更偏记录、归档或即时问答，难以真正进入后续工作推进链路。

### 1.5 1.0 核心结论

1.0 版本不追求做大而全的知识库，也不追求复杂的知识网络。

1.0 要验证的核心结果只有一个：

将用户日常的工作记忆整理成记忆卡后，在用户下次使用时支持自动调用或手动添加调用，并基于这些记忆为用户提供高质量建议，以便进行工作推进和辅助决策。

## 2. 产品功能点及功能优先级

### 2.1 1.0 MVP 设计原则

1. 围绕“沉淀 -> 调用 -> 建议 -> 再沉淀”最短闭环设计。
2. 优先保证记忆卡可沉淀、可管理、可调用、可解释。
3. 优先解决用户真实工作中的连续上下文问题，而不是扩展复杂辅助功能。
4. 先验证建议是否真的能帮助工作推进，再考虑关系网络、复杂助手体系等增强能力。

### 2.2 1.0 MVP 功能列表

#### P0：必须完成

1. **对话入口**
   用户可输入当前问题，发起一次新的工作咨询。

2. **记忆卡手动添加**
   支持用户主动新增记忆卡，补录 AI 未覆盖的工作记忆。

3. **对话后一键沉淀**
   支持将本轮对话中的有效结论手动沉淀为记忆卡。

4. **记忆卡基础结构化**
   每张记忆卡至少包含标题、正文、关键词、来源、创建时间等基础字段。

5. **记忆卡管理**
   支持查看、搜索、编辑、删除记忆卡。

6. **对话中调用记忆卡**
   系统可根据用户问题自动召回相关记忆卡，用户也可手动指定记忆卡参与回答。

7. **基于记忆卡生成建议**
   AI 基于当前问题与调用到的记忆卡，给出更有上下文、更可执行的建议，用于工作推进和辅助决策。

8. **回答中展示引用来源**
   回答中需展示本次参考了哪些记忆卡，提升可信度和可判断性。

9. **调用后继续追问**
   用户可以基于当前上下文继续追问，无需重复描述背景。

10. **API / 模型配置**
    支持基础模型接入与 API 配置，保证 1.0 可独立运行。

11. **账号登录与数据隔离**
    支持账号登录、退出和切换；用户数据按账号隔离，模型配置默认保留。

#### 当前已纳入的配套能力

1. 本地聊天记录保存、搜索、继续查看、重命名和删除。
2. 文件夹管理、首页常用文件夹展示和记忆卡归类。
3. 记忆卡标题、正文及关键词手动修正；对话后手动沉淀仍属于 P0。

#### P1：后续优先补充

1. 在现有人工编辑基础上增强内容纠错；具体范围另行定义。

#### P2：明确不纳入 1.0 范围

1. 记忆网关系自动构建。
2. 复杂关系权重计算。
3. 多助手身份管理。
4. 浏览器插件式内容采集。
5. 企业级知识连接器与跨系统搜索。

### 2.3 1.0 MVP 最终范围结论

1.0 版本以 P0 为实际交付范围。

虽然 P0 清单包含 11 项能力，但本质上聚焦于 5 个核心能力块：

1. **记忆沉淀**：手动添加、对话沉淀、基础结构化。
2. **记忆管理**：查看、搜索、编辑、删除。
3. **记忆调用**：自动召回、手动指定、连续追问。
4. **建议生成**：基于记忆生成建议并展示引用来源。
5. **账号与运行配置**：账号数据隔离，模型 API 与基础参数配置。

## 3. 页面结构及功能点设置

### 3.1 对话页，优先级 P0

#### 页面目标

承载用户发问、记忆调用、AI 回答和连续追问，是 1.0 的主工作台。

#### 核心功能

1. 输入问题并发起对话。
2. 回答后展示已核验的可见记忆引用；不把召回候选一律展示为已使用依据。
3. 发送前支持手动添加或取消选卡；回答前查看并逐张取消自动候选尚未完整实现。
4. 展示 AI 基于记忆生成的建议内容。
5. 展示本轮回答引用了哪些记忆卡。
6. 支持继续追问，并继承当前上下文。

#### 关键规则

1. 未召回记忆时，普通问题仍可基于当前输入和上下文回答，不固定追加“未召回记忆”的说明；缺少必要事实时说明具体缺口，不能编造历史事实。
2. 若召回结果明显不相关，用户可手动调整参与本轮回答的记忆卡。
3. 按问题意图组织回答：事实查询直接给出事实；决策问题给出建议、依据与必要动作；格式修改承接上一轮结果，不因出现“上线”等主题词就强行输出决策建议。

### 3.2 记忆卡沉淀与管理页，优先级 P0

#### 页面目标

承载记忆卡的新增、查看、搜索、编辑和删除，是用户管理工作记忆资产的核心页面。

#### 核心功能

1. 查看全部记忆卡。
2. 按关键词搜索记忆卡。
3. 按关键词或来源筛选记忆卡。
4. 手动新增记忆卡。
5. 编辑已有记忆卡内容。
6. 删除记忆卡。
7. 查看记忆卡详情。

#### 关键规则

1. 记忆卡必须允许人工修正，不能完全依赖 AI 自动结果。
2. 记忆卡管理应突出可查找和可维护，避免长期使用后资产失控。

### 3.3 记忆卡调用能力，优先级 P0

#### 功能目标

确保记忆卡真正进入下一次工作场景，而不是停留在存储层。

#### 核心功能

1. 根据当前问题自动召回相关记忆卡。
2. 支持用户手动选择记忆卡参与本次回答。
3. 发送前展示用户手动选中的卡片；自动候选的回答前预览与干预属于待补齐要求。
4. 回答后展示引用来源，帮助用户判断是否调用准确。

#### 关键规则

1. 用户可见记忆卡的召回结果应可查看和干预；后台隐式记忆不得直接展示为可管理卡片。当前结果展示时机及限制见第 9 章。
2. 记忆调用的目标不是尽可能多，而是尽可能相关。
3. 若系统不确定是否应调用某张记忆卡，应优先减少误调用。
4. 已选 5 张时，点击第 6 张未选卡，显示“最多可添加5张记忆卡”，保留原选择；提示 3 秒后消失，重复点击重新计时。首页卡片和选择弹窗规则一致；取消一张后可继续添加，重复点击首页已添加卡不算超限。

### 3.4 记忆卡沉淀入口，优先级 P0

#### 功能目标

让用户以低成本方式把日常工作信息转化为记忆卡。

#### 核心功能

1. 用户粘贴文本后生成记忆卡。
2. 对话内容可沉淀为记忆卡。
3. AI 自动生成标题与关键词，用户可手动调整。

#### 关键规则

1. 沉淀过程要足够轻，不能让用户觉得“录入成本大于收益”。
2. AI 生成结果不准确时，必须支持人工修改。

### 3.5 API Key 设置页，优先级 P0

#### 页面目标

支撑模型调用和产品运行，是 1.0 的必要配置页面。

#### 核心功能

1. 配置模型 API Key。
2. 配置模型基础参数。
3. 展示连接状态与异常提示。

#### 关键规则

1. 配置失败时要给出明确提示。
2. 模型不可用时要让用户知道当前无法正常获得建议。
3. 模型配置数据不纳入账号数据隔离范围；用户登录、退出或切换账号后，API Key、模型选择和基础参数默认保留。

### 3.6 账号登录与数据隔离，优先级 P0

#### 页面目标

明确账号切换后的本地数据边界，避免不同账号之间串用记忆、后台记忆和聊天上下文。

#### 核心功能

1. 支持账号登录、退出和切换。
2. 按当前登录账号读取用户可见记忆卡、系统后台记忆和聊天记录。
3. 账号切换后重新进入该账号自己的对话上下文，不带入上一账号的聊天记录。

#### 关键规则

1. 数据隔离覆盖用户可见记忆卡、系统后台记忆、聊天记录、会话上下文和召回候选。
2. 账号切换后，当前对话区必须清空或切换为新账号自己的会话，不能继续展示上一账号聊天内容。
3. 模型配置数据不属于账号隔离数据；API Key、模型选择和基础参数默认沿用本机已有设置。

### 3.7 首页、文件夹与历史记录

1. 首页提供提问入口和常用文件夹入口，默认包含客户案例、会议纪要、日常待办、知识沉淀；首页展示文件夹数量为 1—4 个。
2. 记忆卡列表支持文本搜索、文件夹、关键词及来源筛选；详情展示标题、文件夹、更新时间、引用次数、关键词和正文。
3. 文件夹支持新增、重命名；默认文件夹不可删除，自建文件夹删除后卡片转为未分组，不连带删除卡片。
4. 历史记录支持搜索、继续对话、重命名和删除，并按账号保存于本机；不将其描述为云端同步能力。
5. 文件夹用于内容组织，不等同于项目隔离。不能以“客户案例”“日常待办”等分类代替 `project_id`。

### 3.8 手动沉淀与快捷添加交互

1. 主窗口新增或对话沉淀时，用户确认标题、正文、所属文件夹后保存；支持修改关键词。
2. 主窗口“快速解析”辅助生成标题、关键词和推荐文件夹，保留用户输入正文；解析后仍需点击保存，不因解析成功就写入记忆。
3. 桌面端提供独立快捷添加窗口：只输入正文，点击“保存为记忆卡”后解析标题、正文、关键词和分组并直接保存，没有二次确认页。该点击属于明确的用户保存动作；解析失败显示错误，不静默保存。浏览器开发环境使用新增弹窗。
   - 应用运行时默认显示桌面悬浮入口，支持拖动并记住位置；屏幕变化时将入口限制在当前可见工作区内。
   - 点击入口或按 `Command + Shift + M`（Windows：`Ctrl + Shift + M`）在屏幕右侧打开快捷输入框；移除旧的 `Command/Ctrl + P` 触发方式。
   - 设置提供“显示桌面快捷录入入口”开关，记住启停状态；隐藏只影响图标，全局快捷键仍可用。首次隐藏说明快捷键和设置中的恢复入口。
   - 收起快捷窗口保留未提交内容，保存成功后清空；保存失败保留输入供重试。
4. 对话回答支持复制、手动保存；失败回答不提供保存入口。保存失败应反馈原因并保留可修正的输入。
5. 当前文本输入和 Markdown 展示能力，不代表已支持 Word、PDF 等文件导入。

#### 输入与保存规则

| 入口 | 必填与限制 | 保存结果 |
|------|------------|----------|
| 主窗口新增、对话沉淀 | 标题、正文、分组必填；正文输入框最多 2000 字；关键词显示 5 个额度，新增时包含默认标签，但手动新增逻辑尚未硬性拦截超限 | 成功后显示详情；失败保留可修改内容并提示原因 |
| 编辑已有记忆 | 标题、正文必填；可调整分组和关键词 | 更新原卡，不新增副本 |
| 独立快捷窗口 | 正文非空；不能将主窗口的 2000 字输入框限制直接套用于此入口 | 解析后直接保存；分组未匹配时允许未分组；成功通知主窗口并关闭快捷窗口 |

删除记忆卡需要二次确认，界面明确说明删除后无法恢复；当前没有回收站。删除自建分组只取消卡片归属，不删除卡片。

### 3.9 正文格式展示

回答以 `recommendation` 为主，缺少正文时使用 `summary`；有正文时不再拼接摘要和结构化依据文本，引用来源仍在下方引用区展示。保留行动项和不重复的不确定提示，避免同一事实以不同措辞重复出现。

冲突提示同时存在于回答正文和结构化 `uncertainties` 时，前端只展示一次；不同的补充提示仍须保留。此规则只影响展示，新回复生效，已保存的历史消息正文不自动改写。

1. 聊天回答与记忆卡详情共用 Markdown 渲染规则，支持一至六级标题、段落、有序和无序列表、粗体、行内代码、引用及表格。
2. `#### 1. 居家办公试运行相关` 应显示为四级标题，不能将 `####` 原样露出为正文；五级、六级标题遵循相同规则。
3. 标题与后续列表保留清晰间距，聊天区和详情区沿用各自字号，不修改用户保存的原文。
4. 当前为自定义 Markdown 子集渲染，不宣称支持完整 CommonMark、任意 HTML 或富文本编辑。

### 3.10 本周待办与按日期查询安排

**用户目标**：从已保存的工作记忆找回某周、某天的具体安排，减少漏事与重复翻查。

1. 用户通过对话询问“本周有哪些待办”“本周三到周五做什么”；回答可展示待办及其来源记忆。
2. 本周、上周、下周及星期按北京时间解析为具体日期；正文明确日期优先，不把旧卡中的“周三”自动当作本周三。
3. 相对日期以卡片事件时间为优先锚点，缺失时依次参考创建时间、更新时间；单纯编辑不能让旧安排变为本周安排。
4. 周期安排必须在同一句中关联周期和具体行动。“每周三 10 点团队站会”可作为安排；产品介绍中的“每周额度”加另一段的“完成任务、提交 PR”不能拼成用户待办。
5. 查询日期没有匹配记录时，明确返回具体日期及“未找到对应安排记录”；不能用旧对话或手动选中的旧安排填补。
6. 仅部分日期有记录时，应指出有据可查的安排与缺失日期，不臆测剩余安排。
7. 当前按卡片处理日期，混合日期卡可能被保守排除；复杂自然语言日期和事实片段级日期关联仍未完整覆盖。

**边界**：这是记忆中的安排提取与问答，不是独立任务管理或日历系统；没有任务完成状态、日历同步、到点提醒或自动执行能力。

### 3.11 选定资料比较与调用范围

1. 未手动选卡时按问题自动召回；普通非比较问题可在手动卡基础上补充相关自动候选。
2. 已选卡并提出比较、对比或优劣问题时，默认只使用所选资料，不自动添加未选竞品；明确要求补充其他竞品资料后才开放自动候选。
3. “只根据我选的卡”等明确限制优先，不因同一句出现补充资料的表述而解除限制。
4. 仅选择一个产品和一张约束卡时，围绕该产品是否满足约束进行分析，并说明缺少其他比较对象；约束卡不能被当作第二个竞品。
5. 限定模式清除本轮模型输入中的旧对话，防止上一轮比较对象混入；不会删除用户的历史记录。该模式当前也不会补充同一产品未选中的其他卡片。
6. 用户明确要求不使用卡片或记忆信息时，本轮关闭记忆召回与引用；这不等于删除记忆。
7. 手动卡仍受账号、项目、时间与冲突治理约束；选中不代表其事实自动有效。

### 3.12 交互状态与异常处理

| 场景 | 当前行为与产品要求 |
|------|--------------------|
| 空问题、重复发送 | 空白不发送；请求进行中不重复提交 |
| 等待回答 | 显示处理中状态；当前为完整响应后展示，不承诺流式逐字输出 |
| 用户停止回答 | 客户端结束等待并忽略该请求迟到的结果；当前不保证终止服务端或模型计算，也不保证停止计费 |
| 模型配置不完整、调用失败或超时 | 显示可理解的错误，失败消息不提供保存入口；不把失败包装成正常业务结论 |
| 本地服务未启动或连接中断 | 提示本地通信失败；不将其混同为“没有相关记忆” |
| Embedding 或模型重排失败 | 回退关键词或本地排序链路，基础召回仍可继续；效果不等同于增强链路 |
| 记忆存在未解决冲突 | 先说明需要确认的分歧，当前可能整轮澄清，不交给模型任意选边 |
| 引用未确认 | 不将候选卡强行显示为依据；后台隐藏卡不进入用户可管理引用列表 |

### 3.13 数据与运行边界

- 记忆数据由本地 Python 服务和 SQLite 管理，聊天历史保存在当前设备并按账号区分；当前没有多端同步承诺。
- 模型 API 配置为本机共享配置，账号切换后保留；密钥已保存时，设置输入框留空表示不修改，不应理解为清空密钥。
- 模型问答、AI 解析及可选向量和重排会调用配置的模型服务；本地存储不等于全部计算离线。问题、相关记忆和必要上下文可能发送至所配置的服务。
- PC 是产品形态，浏览器入口用于开发预览；不能以某个平台存在构建配置或产物就宣称所有桌面平台均已验收。Windows 部署说明见 [Windows 运行说明](windows.md)。
- 文件夹是用户组织内容的方式；项目、有效时间、替代关系和后台权重属于召回治理，不要求用户维护复杂生命周期状态。

## 4. MVP 核心流程

### 4.1 主流程

1. 用户在工作中产生信息或结论。
2. 用户将内容粘贴到系统中，或从对话中将有价值内容沉淀为记忆卡。
3. 主窗口可通过 AI 辅助生成标题、关键词和推荐分组，用户确认后保存；快捷添加由用户点击保存后完成解析与写入。
4. 用户在下一次工作中输入新问题。
5. 系统自动召回相关记忆卡，用户也可手动补充指定卡片。
6. AI 基于问题和记忆卡生成建议，并展示引用来源。
7. 用户基于建议推进工作或继续追问。
8. 用户将新的结论再次沉淀为记忆卡，形成闭环。

### 4.2 真实工作场景示例

用户是一名产品经理，正在准备下周版本优先级会。

过去一周里，他已经积累了以下工作信息：

- 销售同步了多个客户试用反馈。
- 研发给出了某个功能的实现成本和延期风险。
- 设计评审提出了首页改版建议。
- 老板追问过上个版本延期的原因。
- 用户自己在文档中写下了一段阶段性判断。

在 1.0 产品中，用户可以这样使用：

1. 将上述内容逐步沉淀为记忆卡，部分通过 AI 自动整理，部分手动补录。
2. 在版本会前提问：“这个功能要不要进入下个版本？”
3. 系统自动召回相关记忆卡，如客户反馈、研发评估、历史延期原因和阶段性判断。
4. 用户可手动补充某张关键记忆卡参与本次回答。
5. AI 基于当前问题和相关记忆卡，输出更贴合上下文的建议，例如是否进入版本、主要原因、风险点和建议动作。
6. 回答中展示引用来源，便于用户判断是否调用准确。
7. 会后，用户把最终会议结论再次沉淀为记忆卡，供下一次类似决策继续使用。

## 5. 产品成功判断标准

### 5.1 1.0 核心验证目标

1. 用户是否愿意持续沉淀工作记忆。
2. 用户是否能在下一次工作中真正调用到相关记忆。
3. AI 建议是否比纯通用对话更贴合上下文。
4. 产品是否切实减少了重复解释背景和重复查找历史信息的成本。

### 5.2 关键指标建议

1. 记忆卡创建成功率。
2. 记忆卡被调用率。
3. 引用相关性及用户发现误召回的比例；回答前候选干预未完整实现，暂不把“候选保留率”作为已有可测指标。
4. 用户继续追问率。
5. 用户对建议有效性的主观反馈。
6. 单次任务中因调用记忆而减少的背景补充次数。

## 6. 自动召回技术方案

### 6.1 技术选型结论

1.0 版本的自动召回能力，采用“BM25 关键词召回 + 规则过滤 + 重排”的可运行链路作为当前默认方案；当 embedding 模型配置可用时，再叠加向量检索形成 hybrid RAG（稀疏 + 向量 + 重排）增强链路。

推荐结构如下：

1. BM25 关键词召回：基于标题、正文、关键词、项目名等字段召回候选记忆卡。
2. 作用域与时间硬过滤：先按工作空间、项目、测试快照和 `available_at` / `valid_until` 过滤，再处理语义相关性；未来卡和跨项目卡不得进入自动候选。
3. 重排：综合 BM25 分数、标题/关键词/正文/项目匹配、手动选择优先级、来源权重和意图加权，筛选出最适合本次问题的记忆卡。
4. 实体关联增强：基于客户、联系人、项目和功能等实体关联补充候选并轻量加分。
5. 向量检索增强：当 embedding 模型配置可用时，叠加语义相似召回，并与 BM25、实体候选合并去重后统一排序。2026-10-13 增强：BM25 与向量采用 RRF 融合，高相似语义候选可独立入选；可选模型重排自动候选，失败回退本地排序，仍执行项目、时间与冲突治理。配置与验证边界见 SPEC「混合召回增强」。
6. 2026-10-19 精度优化：清除通用问法中的固定业务扩展，过滤查询泛词并检查最低关键词匹配；通用召回路径对模型重排后的极低相关自动候选进行拒收，手动卡仍优先并执行治理。具体门槛、专项路径边界与回归见 SPEC「召回精度优化」。
7. 周安排按实际日期匹配，旧卡中的“周三”不自动解释为查询当周；正文明确日期优先，编辑时间不自动更新旧安排。无日期匹配记录时明确返回未找到，具体解析边界见 SPEC「召回精度优化」。
8. 手动选卡进行比较时默认限定选中资料；只有明确要求补充其他竞品时才扩展召回。只选一个产品和约束时评估该产品，不擅自增加比较对象。限定模式当前不自动补充同产品的其他卡片。

最终结论：

1.0 自动召回先以 BM25 关键词召回保证低成本、低延迟和可解释；向量检索作为增强能力，不作为无 embedding 配置时的硬依赖。当前默认内容召回阈值为 `0.22`，用于在召回有效信息和屏蔽无效信息之间保持安全余量。

### 6.2 选择该方案的原因

1. 记忆大师当前的核心数据对象是记忆卡，内容以短文本和半结构化信息为主，天然适合检索式召回。
2. 用户提问时，大量工作问题会显式包含项目名、客户名、需求名、时间和事实类型，BM25 比简单关键词重叠更适合做第一层稳定召回。
3. 用户也会出现语义接近但表达不同的历史判断复用需求，因此后续可在 embedding 可用时叠加向量召回，但不能让向量能力成为基础链路阻塞点。
4. 用户需要的是能够真正帮助当前工作的相关记忆，而不是大范围信息铺陈，因此需要通过规则过滤和重排控制最终进入回答的卡片质量。
5. 1.0 版本更强调低延迟、稳定和可解释，BM25 默认召回 + 可选向量增强更适合当前产品落地。

### 6.3 1.0 召回链路设计

建议的召回链路如下：

1. 用户输入当前问题。
2. 系统从记忆卡结构化字段中提取关键词、项目、时间和主题线索。
3. 对查询做轻量同义扩展，用于覆盖口语表达和产品场景表达差异。
4. 先确定工作空间、项目、测试快照和参考日期作用域。
5. 对记忆卡执行硬过滤：跨作用域、`available_at` 晚于参考日期或已过 `valid_until` 的自动卡不得进入候选。
6. 使用 BM25 从标题、正文、关键词、项目字段中召回候选记忆卡。
7. 基于客户、联系人、项目和功能实体关联补充候选；若 embedding 可用，再补充向量候选。
8. 对候选结果进行去重与合并，手动选择的记忆卡默认保留。
9. 综合 BM25、向量、实体、字段命中、项目匹配、来源权重和意图加权进行重排。
10. 最多选出 5 张高相关记忆卡参与回答；不足时允许少于 3 张或零张，不能为凑数加入无关资料。
11. 将最终使用的记忆卡在回答中展示引用来源，并保留作用域过滤诊断。

### 6.4 召回控制策略

为了保证自动召回质量，1.0 需要加入基础控制策略：

1. 用户手动选择加入本轮对话的记忆卡，优先级高于自动召回结果。
2. 用户手动保存或手动编辑过的记忆卡，在召回中拥有更高优先级。
3. 系统后台自动抽取的隐式记忆，默认参与召回，但优先级低于用户主动保留的记忆卡。
4. 长期未命中、被新内容覆盖或调用效果较差的后台记忆，应自动降权。
5. 用户明确说“只根据我选的卡”“只用这些资料”“不补充其他记忆”时，关闭自动补卡，只保留手动指定卡。
6. 用户问题包含明确截至日期时，按该时点的可用信息过滤，避免未来信息穿越；事实发生时间、系统可用时间和录入时间应区分，不能只用创建时间判断。
7. 用户问题包含收入、损失、金额、赔偿、去年等强事实意图时，若卡片没有对应事实类型，应阻止其作为自动召回结果。
8. 当问题明确项目时，先按 `project_id` 过滤，其他项目的同名主题卡不得仅凭关键词进入自动候选。
9. 当同一项目、同一对象、同一事项的候选记忆存在版本变化时，优先依据明确替代关系及事实有效期判断；事件时间提供依据，更新时间仅作辅助，不能单凭“最近编辑”认定事实有效。
10. 当系统对召回结果不确定时，应优先少召回而不是误召回。

记忆卡至少保留以下时间和作用域字段：

- `workspace_id`：工作空间边界。
- `project_id`：稳定的项目标识，不依赖项目显示名称。
- `snapshot_id`：评测或历史场景的记忆快照。
- `event_at`：事实实际发生时间。
- `available_at`：这条记忆从何时起可以被召回。
- `valid_until`：事实失效时间。

### 6.5 记忆更新与陈旧记忆治理方案

#### 6.5.1 产品原则

1. 用户不负责维护复杂的记忆状态。
2. 用户侧只保留两类核心动作：手动保存记忆卡、手动修改记忆卡。
3. 系统负责在后台管理记忆的新鲜度、调用优先级和自动降权。
4. 产品不要求用户理解“陈旧记忆管理”概念，而是通过系统策略保证更合适的记忆被优先调用。

#### 6.5.2 记忆分层

1. **用户可见记忆卡**
   仅包含用户手动保存或手动添加的记忆卡。
   这部分内容用户可以查看、编辑、删除和管理。

2. **系统后台记忆**
   系统可在对话、内容处理和历史沉淀中自动抽取后台记忆，用于支持自动召回和建议生成。
   该类记忆默认不直接展示给用户，也不要求用户进行维护。

#### 6.5.3 陈旧记忆的判断方式

系统不通过显式状态要求用户维护记忆是否过期，而是在后台通过权重变化判断一条记忆是否逐渐失去优先级。

核心判断因子如下：

1. **时间衰减**
   非方法型记忆按事件时间衰减；编辑、引用和最近命中不会自动刷新事实时效。方法型记忆不因年龄自动降权。

2. **新内容覆盖**
   同一事项存在明确且适用的替代证据时，旧内容退出当前事实依据；仅有较新记录不代表已替代。

3. **调用效果反馈**
   若某类记忆参与回答后效果较差，或后续经常被新内容修正，其权重应持续下降。

4. **用户行为信号**
   手动选择表示本轮希望参考；保存和编辑不自动证明事实正确。使用频次暂不用于准确性排序。

5. **来源优先级**
   用户主动保留的显式记忆卡，优先级高于系统后台自动抽取的隐式记忆。

#### 6.5.4 记忆权重机制

1.0 版本不采用复杂状态流转，而采用后台综合权重机制来控制记忆调用优先级。

自动候选统一采用以下初始评分（2026-10-12 已接入，后续通过评测校准，不是正确率承诺）：

| 维度 | 权重 | 当前计算口径 |
|------|------|--------------|
| 相关性 | 60% | 无向量时使用内容召回分；有向量时为 65% 内容分 + 35% 非负向量相似度 |
| 来源先验 | 25% | `quality_weight` 限制在 0—1；可见记忆系数 1.0，隐藏记忆系数 0.6。这是来源先验，不代表用户已经核实事实 |
| 时间适用性 | 15% | 非方法型按事件时间以 180 天尺度衰减；缺失事件时间取 0.5；方法型取 1.0，但仍受明确有效期约束 |

手动保存不豁免过滤；本轮手动选卡优先纳入，不采用“手动 1.0、自动 0.25”的事实可信度比例。引用次数、最近使用时间和编辑时间不参与此统一排序；旧动态权重字段保留兼容，但不驱动新排序。

项目、可用时间、有效期和明确替代关系先于评分；不能用高分挽救不适用的事实。仅正文完全一致且作用域一致的自动卡合并，不再因内容相近就删除可能矛盾的版本。

#### 6.5.5 1.0 管理策略结论

1. 用户只需要决定“哪些记忆值得保存和修改”。
2. 系统负责决定“哪些记忆更应该被优先调用”。
3. 产品不将复杂状态管理暴露给用户。
4. 陈旧记忆默认不删除，而是通过后台权重逐步降低影响力。
5. 用户保存和修改表示内容维护意图，本轮手动指定表示参考意图；这些动作均不豁免适用性及冲突检查。

#### 6.5.6 记忆污染与冲突治理要求

本节是完整 P0 质量要求；2026-10-12 已完成基础治理，具体覆盖范围见第 9 章。相似度和权重只解决排序，不能代替项目、时间及事实有效性判断。

| 场景 | 必须遵循的行为 |
|------|----------------|
| 当前项目明确 | 自动候选先按账号、工作空间、稳定项目标识过滤；同名主题不能使其他项目卡进入当前事实依据 |
| 当前项目不明确 | 可沿用明确且未切换的会话项目；仍有多个合理归属时先澄清，不静默混合各项目事实 |
| 跨项目借鉴或比较 | 用户明确提出后允许引入其他项目经验，但逐项标明所属项目，不改写为当前项目事实 |
| 当前状态查询 | 使用当前时点有效事实；旧方案可解释变化，但不能作为当前结论 |
| 历史回顾 | 区分“当时已知信息”和“事后回顾事件”；前者不得引入后来才可用的记忆，后者应注明补录来源与时间 |
| 新旧信息冲突 | 比较同一对象、同一事项、重叠有效期；有明确替代证据才采用新版本，否则保留分歧并澄清 |
| 手动指定旧卡或跨项目卡 | 允许参考但不默认认定有效，回答说明适用范围；手动选择不豁免账号权限 |
| 会话切换项目 | 同时约束历史消息、会话摘要、可见卡和后台隐式记忆，防止旧上下文绕过召回过滤 |
| 项目或时间字段缺失 | 不自动视为跨项目通用或长期有效；影响结论时提示缺失并请求必要信息 |

时间字段含义：`event_at` 是事件发生时间，`available_at` 是系统可使用该信息的时间，`valid_until` 是有效期结束时间，`created_at` / `updated_at` 是记录维护时间。事件发生不必然等于规则生效；缺少明确生效信息时不得伪造有效区间。`supersedes_id` 表示明确替代关系，`conflicts_with_id` 表示冲突关联；这些字段由后台维护，不要求用户维护生命周期状态，也不引入记忆图谱。

示例：A 项目 8 月计划 9 月上线，9 月确认延期至 10 月；B 项目仍计划 9 月上线。问 A 项目当前排期时采用 A 项目的有效更新，旧计划仅作为变更背景，B 项目不作为 A 项目排期依据。今天补录 8 月旧计划不能覆盖 9 月确认结果。

陈旧记忆可以保留供历史查询，已失效内容不得仅因相关度高、使用频繁或用户编辑过而重新成为当前事实。

### 6.6 当前阶段不采用的方案

#### 1. GraphRAG

当前不作为 1.0 主方案。

原因如下：

1. GraphRAG 更适合复杂关系网络、全局知识推理和大规模图谱场景。
2. 1.0 当前主要目标是提升单次工作问题下的相关记忆召回质量，而不是做复杂关系推理。
3. 在记忆卡数量和关系规模仍有限的阶段，引入图结构建设成本过高，收益不明显。

#### 2. Agentic RAG

当前不作为 1.0 主方案。

原因如下：

1. 多轮 agent 检索链路更复杂，时延和成本更高。
2. 结果稳定性和可解释性相对更弱。
3. 1.0 当前更适合先验证稳定召回和建议质量，而不是复杂自主检索能力。

#### 3. 长上下文直接塞入

当前不作为主检索方案。

原因如下：

1. 成本较高。
2. 随着记忆增多，容易出现上下文污染和信息衰减。
3. 不利于版本管理、记忆降权和精细化调用控制。

#### 4. 无索引文件检索

当前不作为正式方案。

原因如下：

1. 只适合早期 demo。
2. 随着记忆卡规模增长，召回效率和质量都会快速下降。

### 6.8 记忆运行控制层（确定性工作流 Harness）

**已采用**：用确定性工作流组织现有记忆能力，明确每一步的输入、输出、允许的副作用、失败分支和验收条件。Memory 负责保存与召回信息；Harness 负责何时调用、如何约束和验证执行结果。它是运行架构，不要求引入新的 Agent 框架，也不新增用户需要理解或维护的产品概念。

当前已有会话路由、上下文策略、混合召回、基础治理、有限重试和引用检查；2026-10-26 已接入请求级控制器、本地执行记录及聊天/解析预算。查询、解析、手动新增和编辑共享追踪约定，具体契约见技术方案。下表更新关系和防重复保存属于完整目标，H04 尚未交付。

| 流程 | 固定步骤与控制要求 | 用户可见结果 |
|------|--------------------|--------------|
| 查询与回答 | 输入校验 → 会话及作用域识别 → 上下文策略 → 检索与重排 → 适用性及冲突治理 → 生成或澄清 → 输出与引用校验 | 有依据的回答、具体信息缺口或明确失败；格式调整等分支可跳过召回，但不能绕过账号及记忆边界 |
| 手动写入 | 用户主动保存 → 必要的结构化解析与字段校验 → 持久化 → 确认写入结果 | 只有成功写入后才提示保存成功；失败保留输入，同一次保存操作重试不能生成重复卡片。主窗口仅解析仍不写入 |
| 记忆更新 | 用户主动新增或修改 → 判断项目、事项、时间及来源 → 识别替代、并存或未解决冲突 → 建立有依据的更新关系 → 校验当前与历史召回 | 明确更新可用于当前回答；证据不足先澄清，不自动覆盖用户原文，不要求用户维护生命周期状态 |

控制边界：

- 可见记忆只能由用户明确保存或修改产生；后台自动提取只进入隐藏记忆。持续提取闭环仍是后续项，不因引入 Harness 自动升级为已完成能力。
- 新记录不等于新事实；更新判断不得仅依赖创建或编辑时间。优先落地同项目排期变更，局部事实更新不能导致整张卡的其他有效事实丢失。
- 统一约束总耗时、模型调用次数、重试次数和上下文预算；增强检索失败可降级，主模型失败不能伪装成正常回答。客户端停止等待不等于服务端停止执行或计费。
- 引用 ID 有效仅是基础校验，不能据此宣称回答结论均得到证据支持；真实模型效果另行评测。
- 保持 PC 客户端、可见手动记忆、隐藏后台记忆和混合 RAG 方向；运行时按配置使用 BM25 基础链路与可选增强。不引入 GraphRAG、Agentic RAG、多智能体或自主整理循环。
