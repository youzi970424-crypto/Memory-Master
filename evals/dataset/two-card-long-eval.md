# 记忆大师双卡长场景评测集

## 评测目标

验证模型在同时读取两张较长记忆卡和一段复杂办公问题后，能否：

- 正确识别两张卡片分别提供的背景和约束。
- 将两张卡片中的信息合并成一条完整的判断链路。
- 区分事实、推断、风险和待确认项。
- 不把记忆卡内容机械复述成摘要。
- 给出可以直接推动工作的下一步动作。xiang m
- 不编造卡片中不存在的负责人、时间、数据或结论。
- 只输出正常对话答案，不暴露内部 ID、召回过程或隐藏字段。

## 统一输入格式

```json
{
  "query": "用户当前问题",
  "manual_memory_ids": ["记忆卡 ID 1", "记忆卡 ID 2"],
  "conversation_history": []
}
```

## 评测规则

每个用例必须只传入两张记忆卡。模型回答不要求逐字复现对标答案，但必须保留对标答案中的核心判断、行动顺序和风险边界。

如果卡片没有提供负责人、具体日期、预算或实验结果，回答中不得擅自补充。可以将这些内容列为待确认项，并给出建议确认方式。

## 用例 1：新功能是否进入版本

### 场景说明

产品团队收到一项来自重点客户的功能需求。业务方希望尽快承诺交付，研发团队认为当前证据不足，产品经理需要在评审会后给出一个既不拖延、也不冒进的推进方案。

### 记忆卡 1

- ID：`eval-2card-01-a`
- 标题：重点客户反馈：批量导出能力影响续约讨论
- 标签：客户反馈、续约、功能需求
- 内容：

  华东区域的重点客户在最近一次季度回访中反复提出“批量导出项目数据”的需求。客户目前可以逐条下载数据，但无法按照项目、时间范围和负责人一次性导出，导致他们每周需要安排专人整理数据后再制作内部汇报。

  客户认为这个问题已经影响到部门周报和月度经营复盘，客户成功团队判断它会被带入下一轮续约谈判。客户没有明确承诺“没有该功能就一定不续约”，但表示如果下一季度仍没有改善，会重新评估产品的使用范围。

  当前已知信息只有一位客户的明确反馈，尚未统计其他客户是否存在同类问题，也没有完成批量导出需求的使用频率、影响用户数和实际续约金额分析。客户成功团队建议产品团队先给出处理方向，不建议在没有数据的情况下直接对客户承诺具体上线日期。

### 记忆卡 2

- ID：`eval-2card-01-b`
- 标题：需求评审原则：先确认价值，再确定投入
- 标签：需求评审、版本规划、验证
- 内容：

  所有重要需求进入开发前，必须先明确三个问题：第一，需求到底要解决什么业务问题；第二，用什么指标判断它是否有效；第三，在当前版本中优先级是否高于其他工作。

  如果需求的价值判断还不充分，不建议一开始就做完整方案和大规模开发。可以先拆出一个最小可验证范围，例如统计已有客户的真实使用频率、访谈多个角色，或者制作一个低成本原型验证关键流程。

  对来自重点客户的需求，需要同时关注客户价值和产品普适性，不能仅因为单个客户提出就直接将定制需求排进版本。评审结论应明确“当前是否进入验证”“是否进入正式开发”“还缺什么信息”，并为后续动作指定责任人和完成时间。

### 用户问题

> 重点客户把批量导出带到了续约讨论里，业务方希望我们马上答应下个版本支持，研发则认为现在只有一个客户反馈，投入规模和技术方案都还不清楚。产品评审会要求本周给出明确结论。基于这两张记忆卡，请判断这个需求现在应该怎么处理，并给一段可以直接同步给业务、客户成功和研发团队的话。

### 输入参数

```json
{
  "query": "重点客户把批量导出带到了续约讨论里，业务方希望我们马上答应下个版本支持，研发则认为现在只有一个客户反馈，投入规模和技术方案都还不清楚。产品评审会要求本周给出明确结论。基于这两张记忆卡，请判断这个需求现在应该怎么处理，并给一段可以直接同步给业务、客户成功和研发团队的话。",
  "manual_memory_ids": ["eval-2card-01-a", "eval-2card-01-b"],
  "conversation_history": []
}
```

### 对标答案

当前不建议直接向客户承诺下个版本一定上线，也不建议立即进入完整开发。更合适的结论是：本周先把批量导出列为高优先级验证事项，同时评估它是否具有多客户的普适价值。

推进顺序应是：

1. 明确要解决的问题：减少客户整理数据的人工成本，并支持项目、时间范围和负责人维度的汇报。
2. 补充验证数据：访谈其他客户，统计需求出现频率、涉及用户范围和对续约的实际影响。
3. 让研发进行轻量技术评估，明确最小可行范围和大致投入，不必马上进入完整开发。
4. 本周输出“进入验证”还是“进入正式开发”的结论，并补充责任人和完成时间。

可直接同步：

> 批量导出目前被列为重点需求，但基于现有信息还不能承诺下个版本一定上线。本周先完成多客户需求验证和最小方案评估，确认它是否是普遍问题、需要覆盖哪些导出场景以及投入规模。验证结果明确后，再决定是否进入正式开发和版本排期。客户成功团队可以先向客户同步我们已将该问题纳入重点评估，但暂不承诺具体上线日期。

### 通过标准

- 同时使用客户反馈卡和需求评审卡。
- 明确“不立即承诺上线，也不直接进入完整开发”。
- 识别批量导出的核心业务问题，而不是只复述功能名称。
- 提出多客户验证、指标补充和最小技术评估。
- 明确客户成功团队暂不承诺具体上线日期。
- 不编造客户数量、研发工期、续约金额或具体负责人。
- 不输出 `eval-2card-01-a`、`eval-2card-01-b` 等内部 ID。

### 失败判定

- 直接答应下个版本上线。
- 仅回答“需要进一步调研”，但没有给出本周的推进动作。
- 将单个客户需求直接判断为全体客户需求。
- 自行补充具体上线日期、工期或客户数量。

## 用例 2：项目延期后的恢复计划

### 场景说明

一个跨部门项目已经连续两周延期。会议记录里存在明确的阻塞原因和决策，但项目状态卡显示部分工作仍然没有负责人和验收标准。用户需要把两张卡片转化为一份可执行的恢复方案。

### 记忆卡 1

- ID：`eval-2card-02-a`
- 标题：数据看板项目周会纪要：先解决口径和权限
- 标签：会议纪要、数据项目、阻塞
- 内容：

  数据看板项目最近两次周会都出现延期。会议确认目前最主要的阻塞不是前端页面开发，而是三个基础问题没有收口：销售、财务和运营对“有效客户”的统计口径不一致；部分数据表的访问权限还没有开通；历史数据存在缺失，导致测试结果无法稳定复现。

  会议决定先冻结本期指标口径，只保留客户数、回款额和活跃项目数三个核心指标，不再继续扩展指标范围。数据团队负责在本周三前提供一份口径说明和样例数据，信息安全同学负责在本周二前完成测试环境权限开通，产品经理负责组织业务方确认口径。

  会议没有决定是否顺延最终上线日期，也没有确认历史数据缺失由哪个团队负责修复。会议要求下一次周会不再讨论泛化方案，而是逐项检查口径、权限和可复现测试结果。

### 记忆卡 2

- ID：`eval-2card-02-b`
- 标题：项目推进原则：阻塞项必须有负责人和验收条件
- 标签：项目管理、风险、执行
- 内容：

  项目出现延期时，不能只记录“需要跟进”或“尽快解决”，而要把阻塞项拆成具体动作，并为每个动作设置负责人、截止时间和验收条件。

  对跨部门项目，优先处理会阻塞多人工作的上游依赖，例如数据口径、权限、接口和测试环境。只有上游依赖可用后，下游开发和验收才有意义。

  恢复计划不等于重新承诺一个日期。应该先判断当前阻塞项是否已经解除，再根据剩余工作量重新评估上线时间。如果责任归属或验收条件尚未明确，需要在计划中单独列为待确认项，而不是假设它已经有人负责。

### 用户问题

> 数据看板项目已经连续两周延期，业务方希望项目负责人马上给出新的上线日期，但从会议记录看，数据口径、权限和历史数据问题都没有完全解决。请结合这两张记忆卡，帮我整理一份本周的项目恢复计划，并说明现在能不能直接给出新的上线日期。

### 输入参数

```json
{
  "query": "数据看板项目已经连续两周延期，业务方希望项目负责人马上给出新的上线日期，但从会议记录看，数据口径、权限和历史数据问题都没有完全解决。请结合这两张记忆卡，帮我整理一份本周的项目恢复计划，并说明现在能不能直接给出新的上线日期。",
  "manual_memory_ids": ["eval-2card-02-a", "eval-2card-02-b"],
  "conversation_history": []
}
```

### 对标答案

现在不建议直接给出新的最终上线日期。因为当前仍有上游阻塞项未完全收口，尤其是数据口径、测试权限和历史数据缺失会直接影响后续开发验证。可以先给出本周的恢复计划和阶段性检查点，等阻塞项解除后再重新估算上线时间。

本周恢复计划：

1. 周二前：信息安全完成测试环境权限开通，并由项目负责人验证相关人员可以正常访问。
2. 周三前：数据团队输出客户数、回款额和活跃项目数的口径说明及样例数据。
3. 周三或周四：产品经理组织销售、财务和运营确认口径，形成唯一版本并冻结本期指标范围。
4. 同步建立历史数据缺失问题单，明确责任团队、修复范围和验收方式；目前会议记录没有给出责任归属，不能直接假设由数据团队负责。
5. 下一次周会只检查三项结果：口径是否冻结、权限是否可用、测试数据能否稳定复现。三项完成后，再结合剩余开发和验收工作重新评估上线日期。

对业务方的结论可以是：

> 当前先不直接承诺新的最终上线日期。本周优先完成指标口径冻结、测试权限开通和可复现样例数据准备，同时补齐历史数据缺失的负责人和验收条件。待这些上游阻塞项收口后，再基于剩余工作量重新评估上线时间，避免在依赖未解决前重复承诺。

### 通过标准

- 明确当前不能直接给出新的最终上线日期。
- 按时间顺序使用会议卡中已有的周二、周三节点。
- 识别数据口径、权限和历史数据缺失是上游阻塞。
- 对历史数据缺失标记为责任归属待确认。
- 给出负责人、截止时间和验收条件的项目化动作。
- 不擅自推算新的上线日期。

### 失败判定

- 直接给出一个新的具体上线日期。
- 只复述会议结论，没有拆成可执行计划。
- 把历史数据缺失默认归给数据团队。
- 忽略“冻结指标范围”这一已经确认的决策。

## 用例 3：客户续约谈判与报价边界

### 场景说明

客户续约进入谈判阶段，客户对服务质量认可，但对价格上涨和交付范围存在疑虑。两张卡片分别记录了客户真实诉求和公司的报价边界，模型需要帮助用户准备谈判策略，而不是直接承诺折扣。

### 记忆卡 1

- ID：`eval-2card-03-a`
- 标题：北区客户续约沟通：重视稳定性和交付确定性
- 标签：客户、续约、商务沟通
- 内容：

  北区客户使用产品已经两年，核心使用场景是审批流、经营报表和部门协作。客户在续约沟通中没有否定产品价值，反而认可过去一年系统稳定性提升，尤其认可报表访问速度和问题响应效率。

  客户当前最大的顾虑有三个：第一，明年预算比今年更紧，希望价格上涨幅度可控；第二，客户担心新版本功能很多，但真正影响他们日常使用的交付事项不够明确；第三，客户希望问题响应和版本变更能够有固定的沟通窗口，避免每次都临时找人。

  客户提出可以考虑续约两年，但前提是报价结构清晰，并且能在合同或服务说明中明确重点交付范围、服务响应机制和版本沟通方式。客户尚未提出明确预算数字，也没有承诺一定签两年。

### 记忆卡 2

- ID：`eval-2card-03-b`
- 标题：续约报价原则：先确认价值与范围，再讨论优惠
- 标签：报价、合同、折扣边界
- 内容：

  续约谈判不能先从折扣开始。商务沟通应先确认客户认可的价值、下一年度最关键的使用场景和需要纳入交付范围的事项，再根据合同周期、服务范围和资源投入讨论报价。

  如果客户对价格敏感，可以优先拆分基础服务、增值服务和专项交付，避免用一个模糊的总折扣掩盖范围变化。两年期合同可以作为稳定合作的讨论方向，但需要先确认客户内部预算、采购流程和决策人。

  对客户已经提出但公司尚未确认的交付事项，必须标记为待确认，不能在谈判中直接承诺。报价前至少需要形成一版客户需求清单、服务响应边界和交付范围说明，再由商务、客户成功和产品共同确认。

### 用户问题

> 这个客户认可产品价值，但担心涨价、交付不确定和后续没人负责沟通。客户成功希望为了促成两年续约先给折扣，商务想直接报一个总价。基于两张记忆卡，请帮我准备下一轮沟通策略，并写一段既能回应客户顾虑、又不会过度承诺的话术。

### 输入参数

```json
{
  "query": "这个客户认可产品价值，但担心涨价、交付不确定和后续没人负责沟通。客户成功希望为了促成两年续约先给折扣，商务想直接报一个总价。基于两张记忆卡，请帮我准备下一轮沟通策略，并写一段既能回应客户顾虑、又不会过度承诺的话术。",
  "manual_memory_ids": ["eval-2card-03-a", "eval-2card-03-b"],
  "conversation_history": []
}
```

### 对标答案

下一轮不建议先报总价或直接给折扣。应先把客户认可的价值、明年最重要的使用场景和需要明确的交付范围谈清楚，再根据合同周期和服务范围设计报价。

沟通重点：

1. 先确认客户认可的稳定性、报表访问速度和响应效率，说明续约讨论不是单纯价格谈判。
2. 让客户明确下一年度最关键的使用场景，以及哪些交付事项必须写入服务说明。
3. 将基础服务、增值服务和专项交付拆开，避免用模糊折扣掩盖范围变化。
4. 两年续约可以作为方向讨论，但还需要确认预算、采购流程和内部决策人，不能提前判断客户一定会签。
5. 对尚未确认的功能或交付事项，只能记录为待确认项，并由商务、客户成功和产品共同确认后再进入正式报价。

可直接使用的话术：

> 感谢您对系统稳定性、报表访问速度和问题响应效率的认可。关于明年的续约，我们希望先把您最关注的使用场景、重点交付范围和服务响应方式梳理清楚，再给出清晰的报价结构。我们可以一起评估一年和两年合作周期的差异，并将基础服务、专项交付和对应的服务边界拆开说明。对于目前还需要内部确认的交付事项，我们会先列入需求清单，确认范围和责任后再纳入正式方案，避免先承诺但后续交付不清晰。

### 通过标准

- 明确“不先报总价、不先给模糊折扣”。
- 同时回应价格、交付范围和沟通窗口三个客户顾虑。
- 提出拆分基础服务、增值服务和专项交付。
- 将两年续约表述为可讨论方向，而非确定结果。
- 明确未确认交付事项不能直接承诺。
- 话术语气专业、稳妥，可以直接对客户使用。

### 失败判定

- 直接建议给客户一个总折扣。
- 承诺两年续约或承诺具体功能必然交付。
- 只讲价格，不回应交付确定性和服务响应机制。
- 把客户“可以考虑两年”理解成已经确定签两年。

## 用例 4：跨部门上线前的资源取舍

### 场景说明

一个新功能计划在月底上线，但研发资源同时被线上稳定性问题占用，运营希望保留完整营销方案，产品则需要判断哪些内容必须进入首发版本、哪些可以延后。两张卡片分别提供上线原则和当前资源事实。

### 记忆卡 1

- ID：`eval-2card-04-a`
- 标题：新功能上线原则：首发版本只保留关键闭环
- 标签：上线、版本范围、MVP
- 内容：

  新功能首次上线时，优先保证用户能够完成最核心的业务闭环，包括进入功能、完成核心操作、看到结果并获得必要的异常提示。首发版本不应为了满足所有设想而一次性加入复杂配置、低频报表和非关键的个性化能力。

  进入首发版本的内容需要满足至少一个条件：它直接影响核心业务闭环，或者是合规、数据安全和稳定性所必需。如果某项需求主要用于营销展示、提升长期使用深度或服务少量特殊场景，应先评估是否可以放到后续迭代。

  上线评审时必须明确首发范围、延期范围、验收标准和上线后的观察指标。范围收缩不是简单删功能，而是要确保被保留的版本仍然能够被用户理解、使用和验证。

### 记忆卡 2

- ID：`eval-2card-04-b`
- 标题：本月底上线项目状态：稳定性问题占用研发资源
- 标签：项目进展、资源、上线风险
- 内容：

  新功能当前计划月底上线，核心流程已经完成开发，基础测试正在进行。剩余工作包括异常提示补齐、权限校验复核、运营后台报表、营销落地页和一组个性化配置。

  与此同时，线上已有一个影响部分客户的稳定性问题，研发需要投入人力排查和修复。当前没有证据表明该问题一定会导致新功能延期，但如果继续按完整范围推进，测试和上线准备的缓冲时间会明显减少。

  产品、研发和运营尚未形成一致的范围决策。研发倾向于优先完成异常提示和权限校验，运营希望营销落地页和完整报表随首发上线，业务方则希望月底能对外宣布新功能。当前没有明确记录谁拥有最终范围决策权，也没有给出个性化配置的客户使用数据。

### 用户问题

> 新功能核心流程已经完成，但线上稳定性问题占用了研发资源。研发希望先保异常提示和权限校验，运营希望完整报表和营销落地页也一起上线，业务方又要求月底对外宣布。请结合两张记忆卡，帮我判断首发版本应该保留什么、延期什么，并给出一个可以用于跨部门对齐的结论。

### 对标答案

首发版本应优先保留能够完成核心业务闭环、保障安全和稳定性的内容，不建议在研发资源已经被线上问题占用时继续按完整范围推进。

建议首发保留：

1. 核心流程本身，确保用户可以进入功能、完成核心操作并看到结果。
2. 异常提示，保证用户在失败或异常情况下知道发生了什么。
3. 权限校验，作为数据安全和功能可用性的必要条件。
4. 基础测试和上线验收，不能因为月底对外宣布而省略。

建议延期或拆分验证：

1. 个性化配置：当前没有客户使用数据，先作为后续迭代或小范围验证项。
2. 完整运营后台报表：如果不是首发核心闭环和上线观察所必需，可以先保留最小监测指标，完整报表后续补齐。
3. 营销落地页：可以与产品首发解耦，先准备对外说明或轻量页面，不应挤占核心功能、权限和稳定性工作的资源。

跨部门对齐结论：

> 本月底目标先保证新功能安全、稳定地跑通核心闭环，而不是一次性上线全部配套能力。首发范围暂定为核心流程、异常提示、权限校验和必要的基础监测；个性化配置、完整运营报表和营销落地页先拆为后续交付或独立验证项。线上稳定性问题优先级不降低，最终是否按月底对外宣布，需要在首发范围、验收标准和风险确认后再决定。当前尚未明确范围决策人，需先指定最终拍板角色，避免跨部门继续并行争论。

### 通过标准

- 明确以核心闭环、安全和稳定性作为首发优先级。
- 保留核心流程、异常提示和权限校验。
- 对个性化配置标记为数据不足、需要验证。
- 能区分完整报表与最小监测指标。
- 将营销落地页与核心产品上线解耦。
- 指出当前没有明确范围决策人。
- 不擅自承诺月底一定上线或一定延期。

### 失败判定

- 因为业务方要求对外宣布，就建议所有内容全部首发。
- 直接删除线上稳定性问题，不纳入上线判断。
- 把没有客户数据支持的个性化配置直接列为首发必做。
- 给出“月底一定上线”或“月底一定延期”的确定结论。

## 统一评分建议

每个用例建议按 10 分评估：

| 评分项 | 分值 | 判断标准 |
| --- | ---: | --- |
| 两张卡片都被正确使用 | 2 | 回答同时体现两张卡片的关键事实或原则 |
| 核心结论准确 | 2 | 没有偏离对标答案的主要判断 |
| 行动方案可执行 | 2 | 有明确动作顺序、检查点或推进方式 |
| 风险和不确定性处理 | 2 | 能标记缺口，不把未知信息说成事实 |
| 输出自然且可复用 | 1 | 适合直接同步、转发或执行 |
| 没有内部信息泄露 | 1 | 不出现记忆卡 ID、召回过程或系统提示词 |

### 评分结果解释

- 9-10 分：通过，可作为稳定回归样例。
- 7-8 分：基本通过，但需要检查遗漏的风险或行动项。
- 5-6 分：部分通过，两张卡片综合不足。
- 0-4 分：不通过，存在误用记忆、编造事实或结论方向错误。
