# SPEC｜记忆大师 1.0（记忆沉淀与调用）

> 活文档。版本：v0.4（2026-10-26）。产品需求以 [PRD](product-design.md) 为统一入口；本文件描述技术约束，当前实现差距见 PRD 第 9 章。

## 1. 输入

- 格式：JSON，描述一次用户工作咨询及可参与本轮处理的记忆信息。
  ```json
  {
    "session_id": "s001",
    "user_id": "u001",
    "query": "这个功能要不要进入下个版本？",
    "manual_memory_ids": ["m101", "m205"],
    "candidate_memories": [
      {
        "memory_id": "m101",
        "source_type": "manual_visible | system_hidden",
        "title": "客户A试用反馈",
        "content": "string",
        "keywords": ["版本规划", "客户反馈"],
        "project": "增长中台",
        "created_at": "2026-08-28T10:00:00+08:00",
        "updated_at": "2026-08-29T14:00:00+08:00",
        "last_used_at": "2026-08-30T09:00:00+08:00",
        "source_weight": 1.0,
        "quality_weight": 0.86
      }
    ],
    "context": {
      "product_area": "版本规划",
      "current_project": "增长中台",
      "turn_type": "new_task | follow_up | format_revision | correction | topic_switch",
      "resolved_query": "由服务端根据当前问题和对话状态生成的本轮工作问题",
      "conversation_state": {
        "active_topic": "当前持续讨论的主题",
        "previous_user_query": "上一轮用户问题",
        "previous_answer": "上一轮最终可见回答",
        "format_constraints": {}
      },
      "conversation_history": [
        { "role": "user | assistant", "text": "string" }
      ]
    }
  }
  ```
- 边界：
  - `query` 必填，长度 1-2000 字；为空直接报错，不静默补全。
  - `manual_memory_ids` 服务端最多 10 张；超过则报错并提示用户缩减。当前客户端最多选择 5 张，两个限制尚未统一。
  - `candidate_memories` 单轮候选最多 200 张；进入最终回答的记忆最多 5 张。
  - 非手动指定的记忆卡在无 embedding 配置时走 `bm25_keyword_fallback`，需达到内容召回阈值 `content_recall_score >= 0.22`，并通过最小字段重叠、强意图、项目和时间边界过滤；手动指定的记忆卡不受该阈值限制。
  - 当 embedding 模型配置可用时，允许进入 `hybrid_rag`，自动卡仍需满足语义相似度 `vector_score >= 0.85` 与基础相关性过滤。
  - 单张记忆 `content` 建议不超过 500 字；超出时允许进入检索，但注入模型前必须做截断或摘要。
  - `source_type` 仅允许 `manual_visible` 或 `system_hidden`。
- `conversation_history` 可为空；为空时按新对话处理。
- 上下文判定先识别本轮类型，再决定历史和记忆卡的作用：新问题降低旧上下文权重；追问、格式修改和纠正必须承接上一轮结果；明确换题时隔离上一话题。
- `resolved_query` 用于记忆召回，不能把全部历史文本直接拼接到检索问题中。
- 所有 `candidate_memories`、`manual_memory_ids`、`conversation_history` 和 `session_id` 必须归属于当前 `user_id`；账号切换后不得沿用上一账号的聊天记录、会话上下文或召回候选。
- 数据来源：
  - 用户手动保存或手动添加的可见记忆卡。
  - 系统后台自动抽取的隐式记忆。
  - 当前用户发起的工作问题与上下文信息。
  - 模型配置数据不作为召回或会话数据来源，不参与账号数据隔离。

## 2. 输出

```json
{
  "answer": {
    "summary": "一句话建议，≤80字",
    "recommendation": "给用户的主要建议正文",
    "reasoning_points": [
      { "text": "建议依据1", "memory_ids": ["m101"] }
    ],
    "action_items": [
      { "text": "下一步建议动作", "priority": "high | medium | low" }
    ],
    "uncertainties": [
      { "text": "当前仍不确定的信息点", "memory_ids": [] }
    ]
  },
  "memory_usage": {
    "selected_memory_ids": ["m101", "m205"],
    "manual_memory_ids": ["m101"],
    "auto_recalled_memory_ids": ["m205"],
    "dropped_memory_ids": ["m301"],
    "citation_count": 2
  },
  "memory_capture": {
    "should_save": true,
    "suggested_memory_card": {
      "title": "版本优先级判断：功能是否进入下个版本",
      "content": "本轮形成的有效结论摘要",
      "keywords": ["版本规划", "需求判断"],
      "source": "conversation"
    }
  },
  "meta": {
    "retrieval_mode": "bm25_keyword_fallback | hybrid_rag | disabled",
    "generated_at": "2026-08-31T15:00:00+08:00",
    "model": "string",
    "query_tokens": 0,
    "retrieved_count": 0,
    "used_count": 0
  }
}
```

- `summary` 必须是明确建议，不得只复述问题。
- `reasoning_points` 每条至少绑定 `0-3` 个 `memory_ids`；若无支撑记忆，必须进入 `uncertainties`，不能伪造依据。
- `action_items` 可为空，但若用户问题本身要求推进动作，至少输出 1 条。
- `selected_memory_ids` 必须是 `manual_memory_ids + auto_recalled_memory_ids` 的去重集合。
- `suggested_memory_card` 只是建议沉淀内容，不等于自动替用户保存；最终保存动作仍需用户手动触发。

## 3. 处理规则

- 自动召回采用 BM25 默认召回 + 可选向量增强：
  - 无 embedding 配置时，使用 BM25 关键词召回，检索字段包括标题、正文、关键词和项目。
  - 有 embedding 配置时，叠加向量检索召回语义相关记忆。
  - 合并去重后进行重排，选出 Top 3-5 张进入回答。
  - 严格指定模式下关闭自动补卡，只保留用户手动指定记忆。
  - 明确截至日期的问题过滤日期之后的自动卡。
  - 强事实意图问题需要事实类型匹配，否则丢弃低依据卡片。
  - 同项目、同对象、同事项的版本优选以明确替代关系和事实有效期为准，事件时间提供依据，更新时间仅作辅助；无法解决的冲突必须说明并澄清。当前相似卡优选仅部分覆盖该要求，见 PRD 6.5.6 与第 9 章。
- 用户手动指定的记忆卡优先级高于自动召回结果，且默认保留供参考；手动选择不保证事实当前有效，不豁免账号权限，旧卡或跨项目卡须说明适用边界。
- 用户手动保存或手动编辑过的记忆卡，权重高于系统后台自动抽取的隐式记忆。
- 系统后台隐式记忆允许参与召回，但默认不直接展示给用户，也不进入用户可管理列表。
- 陈旧记忆不通过显式状态暴露给用户，而在后台通过权重衰减处理。
- 账号数据隔离覆盖用户可见记忆卡、系统后台记忆、聊天记录、会话上下文和召回候选；模型配置数据（API Key、模型选择、基础参数）默认保留，不随账号切换清空。
- 记忆权重至少参考以下因子：
  - 当前问题相关度
  - 新鲜度
  - 历史使用价值
  - 被新内容覆盖或修正的程度
  - 记忆来源权重
- 回答必须区分“有依据的建议”和“不确定信息”。
- 若某条建议无法从记忆中获得支持，可基于通用模型能力补充判断，但必须进入 `uncertainties` 或明确标注“需要补充信息”，不能伪装成已被记忆支持的结论。
- 用户可见记忆卡只允许在用户手动保存、手动添加或手动修改时发生变化。
- 禁止行为（不管置信度多高）：
  - 禁止把系统后台隐式记忆直接展示成用户已保存的记忆卡
  - 禁止伪造 `memory_id`
  - 禁止引用未参与本轮回答的记忆作为依据
  - 禁止把没有明确来源支持的判断写成确定结论
  - 禁止在未经过用户操作的情况下自动替用户保存记忆卡

### 混合召回增强（2026-10-13）

- BM25 与向量分别取前 20 个正分候选，混合模式用 RRF（k=60）融合排名。归一化 RRF 与原相关性各占 50%，再沿用相关性 60%、来源 25%、时间 15% 的排序权重；无 embedding 时保留原关键词排序。
- 高相似语义候选（当前沿用 `vector_score >= 0.85`）不再要求关键词重叠，但仍受账号、项目、时间和强事实意图过滤。该阈值需要按实际中文 embedding 模型评测，不能理解为 85% 的正确概率。
- 可选模型重排只处理通过过滤的自动候选，最多 40 张，手动指定卡不送入重排且优先保留。重排相关性继续结合来源、时间权重；事实冲突与替代版本治理仍在生成前执行。
- 服务端环境变量 `MEMORY_MASTER_RERANKER_URL` 为完整的 Cohere-compatible 重排端点，`MEMORY_MASTER_RERANKER_MODEL` 为模型名，`MEMORY_MASTER_RERANKER_API_KEY` 为可选 Bearer 密钥（本地无认证服务可留空）。当前未增加客户端配置表单；`.env.example` 仅是模板，启动服务前需要将变量导出到进程环境。
- 请求使用 `model/query/documents/top_n`；响应必须包含全部候选的 `results[{index,relevance_score}]`，分数为有限的 0–1 数值。此协议不代表兼容所有厂商原生接口；例如不同结构的原生 DashScope 接口需要适配，不能直接填写。
- 未配置重排时使用本地排序；8 秒超时、网络错误或异常响应时回退，不阻塞回答。响应 `meta` 提供 `fusion_mode`、`reranker_used`，失败时提供不含服务响应正文的 `reranker_error`。
- 验证：`python3.12 -m unittest evals.test_hybrid_retrieval` 覆盖语义独立召回、隔离边界、RRF、重排协议及降级。测试使用模型替身，不代表真实中文效果验收。

### 召回精度优化（2026-10-19）

- 手动选卡的比较/对比请求默认限定为选中资料，不自动加入未选竞品；明确要求补充其他竞品资料时才开放自动候选，显式“只根据选中资料”优先。普通非对比请求仍沿用原混合召回规则。
- 限定对比在候选检索前过滤未选卡，并清除本轮模型输入中的旧对话，避免之前的竞品比较污染本轮。约束卡不视作竞品；只选一个产品时按约束评估并说明其他比较对象缺失。此实现保守限制全部补充资料，尚未支持仅补充同一产品其他卡片。

- 周安排查询增加日期校验：将本周/上周/下周及指定星期解析为北京时间具体日期，统一约束普通召回、手动卡、本周待办和居家办公专项路径。日期匹配可独立补充候选，避免“周三”检索不到写作“2026-10-21”的安排。
- 正文明示日期优先；相对星期使用 `event_at`、`created_at`、`updated_at` 顺序确定锚点，单纯编辑旧卡不刷新旧安排所属周。明确每天/每周重复的安排按周期匹配。没有目标日期证据时直接返回“未找到对应安排记录”，不让模型用旧答案填补；向模型提供具体查询日期及卡片创建、更新时间。
- 当前日期解析覆盖周查询、常见年月日和星期范围；混合日期卡保守排除，尚未实现事实片段级日期关联。周期规则、复杂自然语言日期与部分日期缺失仍需扩大评测；部分缺失由生成规则明确标注，不代表完整日历引擎。

- 查询扩展仅保留同义表达，不再根据“哪些信息”“周五”“三个客户”“提前准备”等通用表达补入订单字段、固定日期、客户名单或办公风险。
- BM25 查询词过滤“需要、哪些、信息”等泛词；关键词入选要求至少匹配两个不同的查询词元，只有一个有效词元的短查询允许匹配一个。此限制仅用于关键词路径，不阻止高相似向量候选或手动指定；已有意图加分路径仍保留。
- 模型重排成功时，低于 `MEMORY_MASTER_RERANK_THRESHOLD`（默认 `0.10`）的自动候选不进入通用召回结果。过滤使用原始重排相关性，来源和时间权重不能把低相关候选抬回；手动卡不受该门槛影响，仍执行事实治理。未配置或调用失败时保留本地排序。
- 响应 `meta.reranker_rejected_count` 记录该阶段拒收数量，不暴露隐藏记忆内容。此过滤作用于通用 `retrieve` 路径，本周待办补卡和本地专项路径仍单独处理。
- 新增 `python3.12 -m unittest evals.test_retrieval_accuracy`：同时验证目标命中、额外卡排除、无相关资料、短查询和手动指定。默认重排门槛只是保守初值，尚未通过真实中文重排模型校准；这些定向回归不代表总体业务准确率。

### 3.1 当前召回治理实现（2026-10-12）

- 自动候选统一排序：`0.60 * relevance + 0.25 * source_reliability + 0.15 * temporal_applicability`。来源为先验而非事实认证；引用次数不再进入排序。
- 手动卡优先纳入，不再向模型传递手动 1.0 / 自动 0.25 的可信度权重。范围不符或已有有效替代版本时先澄清。
- `previous_retrieval_scope` 为客户端回传的上一轮作用域，仅用于追问；新问题不默认继承，项目改变时移除旧历史。服务端当前问题明确识别的项目优先。
- 未指定参考时间使用当前时间，过滤未来可用和失效记忆。全部召回路径在生成前再次治理。
- 仅同作用域、正文完全相同的自动卡去重。明确 `conflicts_with_id` 或同标题的标注事实差异触发 `generation_mode=clarification`，停止业务答案生成；任意自然语言事实识别仍未完成。
- 响应 `meta` 增加 `retrieval_scope`、`ranking_weights`，可见引用携带 `ranking_signals`；冲突提示不暴露隐藏记忆。
- 验证与边界见 PRD 10.4；当前保守策略可能整轮澄清，后续需评测有效召回及误拒答。

### 3.2 格式与污染治理补充（2026-10-09）

- 聊天与详情共用 Markdown 子集渲染，支持一至六级标题、段落、列表、粗体、行内代码、引用和表格；四至六级标题已补齐，桌面视觉验收待完成。
- 项目明确时按稳定项目标识约束自动召回；不明确且无法从当前会话唯一判断时，应澄清，不默认混用所有项目事实。
- 当前状态与历史回顾按各自参考时间处理；当前状态不得仅靠权重衰减排除失效内容。
- 会话项目切换、手动卡、后台隐式记忆和跨项目借鉴均须遵循 PRD 6.5.6；这些是完整治理目标，不代表全部已实现。

### 3.3 Harness 接口与预算（2026-10-26）

查询、记忆解析、新增和编辑接入统一执行上下文；具体输入、输出、副作用和失败契约见 [技术方案](plan.md) 的 Harness 运行控制章节。保存与编辑保持用户主动操作，后台隐藏记忆不进入用户卡片列表。

- 成功响应增加 `meta.harness`：`request_id`、`version`、`elapsed_ms`、`provider_calls`、`total_tokens`、`usage_complete`、`trace_persisted`。原业务字段保持兼容；`total_tokens=null` 表示有实际调用缺少可核实用量，无调用时为 0。
- 聊天/解析共享 90 秒处理预算及最多 12 次供应商调用；准备阶段最多使用开始后的 20 秒，并预留 4 次调用给生成与校验。每次外发 JSON 最多 48,000 个 Unicode 字符；这不是 Token 计数。
- 预算错误码：`harness_timeout`、`harness_call_limit`、`harness_context_limit`。聊天仍返回既有回答结构，`generation_mode=model_error`、`memory_capture.should_save=false`；解析失败返回 HTTP 400，包含错误码与请求 ID，不写卡片。
- 当前实现是阶段边界及网络读取的协作式预算，不承诺中断阻塞的系统调用或停止供应商计费。可选阶段预算不足可降级，全局预算耗尽后不再发起模型请求。
- SQLite `harness_runs` 保存按账号隔离的本地记录；响应摘要不包含阶段原始记录。记录保留与隐私细节见技术方案；记录失败不覆盖已提交的业务成功结果，以 `trace_persisted=false` 标明。
- `GET /api/health` 增加 `harness_version: "1"`。新增表采用 `CREATE TABLE IF NOT EXISTS`，不重建已有记忆表。

## 4. 失败兜底

| 失败情形 | 处理 |
|----------|------|
| 未召回到相关记忆 | 直接基于当前问题和对话上下文回答，不追加未召回记忆的说明；仅在缺少回答所需的具体事实时说明缺口 |
| 自动召回结果明显不相关 | 丢弃低相关结果，仅保留手动指定记忆卡，并提示用户补充或调整 |
| 用户要求只根据选中资料回答 | 关闭自动召回补卡，仅使用手动指定记忆卡；若指定卡不存在，返回缺失提示 |
| 用户问题包含明确截至日期 | 按当时可用信息和有效期过滤；手动卡可保留参考，但不得作为当时已知事实，需说明时间边界 |
| 手动指定记忆卡不存在 | 忽略该卡并返回提示，不影响其他流程 |
| 候选记忆过多导致超长 | 先截断候选数量，再通过重排只保留 Top 3-5 张 |
| 某张记忆内容过长 | 先摘要或截断，再参与模型注入；原始记忆不被覆盖 |
| 模型生成建议但依据不足 | 将对应内容写入 `uncertainties`，不进入确定性建议 |
| 模型调用失败或超时 | 主模型可恢复网络错误和限流最多重试 2 次，受局部与 Harness 总预算约束；超时和输出截断不重复同一请求，明确反馈错误并保留输入 |
| 输出 JSON 不合法 | 最多重试 2 次（带格式纠正），所有尝试计入同一预算；仍失败按模型失败处理 |
| Harness 总耗时、调用次数或生成上下文超限 | 返回明确预算错误，不继续发起模型请求，不产生可保存的正常建议 |
| 本地执行记录写入失败 | 保留业务结果，返回 `meta.harness.trace_persisted=false`；不把已成功保存误报为失败 |

## 5. 评估标准（L12）

- 测试集：至少 20 组构造工作场景数据，覆盖：
  - 正常召回 8 组
  - 无高相关记忆 4 组
  - 新旧记忆冲突 3 组
  - 手动指定与自动召回混合 3 组
  - 超长候选记忆 2 组
- 指标与及格线：
  - 召回可用率 ≥90%
  - 最终回答中引用的记忆相关性人工判定 ≥90%
  - 手动指定记忆保留率 = 100%
  - 无依据确定性结论数 = 0
  - 后台隐式记忆误展示给用户次数 = 0
  - 在“无高相关记忆”场景下，不追加未召回记忆说明；确实缺少必要事实时准确说明具体缺口，正确率 = 100%
  - 用户主观评价“建议比无记忆对话更有帮助”比例 ≥70%
- LLM-as-Judge 可辅助判断：
  - 建议是否真正使用了引用记忆
  - `uncertainties` 是否如实暴露了信息不足
  - 是否把无依据判断错误包装成确定性建议

## 成本账（CPT 估算）

- 单轮工作问题建议链路：BM25 关键词召回 1 次 + 规则过滤与重排 1 次 + 主模型生成 1 次；当 embedding 配置可用时，额外增加向量检索 1 次。
- 在记忆卡规模较小的 1.0 阶段，BM25 默认召回成本显著低于“把全部记忆直接塞入长上下文”方案，且更利于做权重治理、来源控制和引用展示；向量检索作为增强链路按配置启用。
- 若单轮最终只注入 Top 3-5 张记忆卡，模型侧成本和延迟可控，适合 PC 端工作流场景。
