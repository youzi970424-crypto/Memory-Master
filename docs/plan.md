# PLAN｜记忆大师 1.0 技术方案

> Plan Mode 讨论后定稿。当前阶段以固定工作流为主，核心是“记忆沉淀 + BM25 默认召回 + 建议生成 + 用户手动保存”，不做复杂 Agent 编排；embedding 配置可用后再增强为混合召回。

## 当前实现校准（2026-10-09）

产品需求与交付状态统一见 [PRD](product-design.md)，下文原架构和阶段划分保留为方案背景，不能直接当作完成状态。

- 当前代码为 `src/`（React + TypeScript、自定义 CSS）、`src-tauri/`、`services/api/server.py`；SQLite 默认文件为 `storage/memory_master.db`。下方分层目录和 shadcn/ui 属于原规划，不表示已按该结构落地。
- 聊天记录和用户确认后的一键沉淀已有实现，不再作为尚未开展的 Phase 3 功能；后台隐式记忆持续抽取闭环仍需补全。
- 2026-10-12 已接入统一 60/25/15 自动评分、上一轮作用域回传、当前时间默认过滤及基础冲突澄清；自然语言事实识别和局部替代仍待完善，详见 PRD 6.5.6、第 9—10 章。
- 新旧版本不得只按编辑时间选择；手动卡优先供参考不等于其内容在当前项目和时间有效。
- 开发使用 `pnpm dev`，桌面开发使用 `pnpm desktop:dev`，构建及类型检查使用 `pnpm build`；专项评测命令见 `package.json`。本次文档整理未执行全量产品评测。

## 技术栈及理由

- **客户端：Tauri + React + TypeScript**：产品形态明确为 PC 客户端，Tauri 更轻量，资源占用和分发成本优于 Electron，适合 1.0 阶段的桌面工作台产品。
- **前端 UI：React + shadcn/ui**：适合构建对话区、记忆卡列表、引用来源、设置页等高密度桌面信息界面。
- **后端能力：Python 3.12 服务层**：适合实现记忆沉淀、检索编排、权重计算、评测脚本和数据处理。
- **模型链路：BM25 默认召回 + 可选混合 RAG**：当前默认使用 BM25 关键词召回 + 规则过滤 + 重排 + 主模型生成；embedding 配置可用后再叠加向量检索，适合当前记忆卡短文本、半结构化、可解释召回场景。
- **存储：SQLite / PostgreSQL + 向量索引**：1.0 可先用 SQLite 承载结构化数据，配合向量索引能力；若后续并发或团队化需求提升，再切 PostgreSQL。
- **不做重型图数据库**：当前不引入 Neo4j，不做 GraphRAG，避免前期系统复杂度过高。

## 架构与数据流

```text
用户输入问题
  → query_validate        输入校验 / 空输入拦截 / 长度限制                [纯代码]
  → retrieve_bm25         BM25 关键词召回（标题/正文/关键词/项目）       [纯代码]
  → retrieve_vector       向量检索（embedding 可用时启用）              [向量检索]
  → merge_rerank          去重合并 + 规则过滤 + 重排 + Top 3-5           [纯代码/重排]
  → memory_weight_filter  来源权重 / 新鲜度 / 使用价值 / 覆盖关系降权    [纯代码]
  → answer_generate       基于问题 + 记忆生成建议、依据、动作项          [主模型调用]
  → cite_render           输出引用来源、区分不确定信息                  [纯代码]
  → save_suggestion       生成可保存的记忆卡建议，不自动替用户保存       [纯代码]

用户手动保存内容
  → memory_parse          标题/关键词/正文结构化                        [模型调用]
  → memory_store          写入用户可见记忆卡                            [数据库]

系统后台沉淀
  → hidden_memory_extract 从对话/处理中抽取隐式记忆                     [模型调用]
  → hidden_memory_store   写入系统后台记忆，不直接展示给用户            [数据库]
```

容错重点：
- 未召回相关记忆时，直接基于当前问题和对话上下文回答，不追加未召回记忆的说明；仅在缺少必要事实时说明具体缺口。
- 某条隐式记忆质量较差，不应影响整轮回答；可在重排或权重过滤阶段直接丢弃。
- 用户手动指定的记忆卡优先级最高，不因自动召回质量波动而丢失。
- 账号切换时必须重置当前会话上下文并按当前账号重新读取数据；聊天记录、记忆卡和后台记忆不得跨账号带入。

## Harness 运行控制实现（2026-10-26）

采用现有服务内的请求级控制器，复用确定性工作流，不新增 Agent Loop 或框架依赖。`harness_flow` 建立请求上下文，`harness_stage` 记录阶段和检查截止时间，`provider_json` 统一约束模型网络调用。`ContextVar` 隔离并发请求，结束时无论成功或失败都清理上下文。

### 执行契约

| 入口与输入 | 执行与输出 | 允许的副作用 | 失败分支 |
|------------|------------|--------------|----------|
| `handle_chat`：当前问题、历史、所选卡、作用域；身份由认证接口传入 | 校验 → 会话路由 → 召回或跳过 → 统一治理 → 生成、澄清或本地分支 → 引用检查；返回既有回答结构及 `meta.harness` | 更新索引缓存、实际引用计数和执行记录；不创建可见卡片 | 非法输入报错；冲突返回澄清；预算耗尽返回 `model_error` 且 `should_save=false`；增强失败优先走本地路径 |
| `handle_memory_parse`：原始内容、标题与候选分组 | 校验 → 有界模型解析 → 结构校验；返回草稿及 `meta.harness` | 仅写执行记录 | 解析、格式或预算错误明确反馈，不创建卡片 |
| `handle_memory_create`：用户主动保存的卡片 | 校验必填字段及所属分组 → 写卡片与实体索引 → 提交；返回已保存卡片及 `meta.harness` | 写当前账号可见卡片、索引与执行记录 | 提交前异常回滚，不报成功；没有新增自动保存或保存重试语义 |
| `handle_memory_update`：目标 ID 与用户修改字段 | 按账号和可见性读取 → 校验分组 → 更新及提交；返回卡片及 `meta.harness` | 更新指定卡片、索引与执行记录 | 不存在或跨账号返回未找到；提交前异常回滚。自动事实替代、局部版本更新仍属于 H04 |

写入事务提交后，观测记录失败不反转业务成功，避免用户因误报失败重复保存。新增与编辑仅接入执行追踪，保留已有数据库事务边界；H04 的防重复保存与事实版本语义未在本轮加入。

### 预算与降级

- 聊天与解析每次请求共享 **90 秒**处理预算，最多 **12 次**实际供应商调用；所有重试计入同一额度。分类、embedding、重排、主模型和引用验证均经统一出口。
- 分类、embedding 和重排共用请求开始后的 **20 秒**准备窗口，并预留 **4 次**调用给生成及引用检查。准备预算不足时走原有规则分类、BM25 或本地排序。引用验证失败或上下文超限沿用本地引用检查，不将此检查宣称为完整事实支持验证。
- 主模型与解析最多尝试 3 次；主模型已有 60 秒局部预算继续生效，实际网络超时取局部和全局剩余时间的较小值。重试等待也检查剩余预算。超时或输出截断不重复同一主模型请求。
- 每次外发 JSON 限 **48,000 个 Unicode 字符**，包括系统指令与序列化上下文；这是可复现的字符上限，不是假定的 Token 数。可选阶段超限则降级，生成或解析超限则明确报错；不为塞入预算静默删掉用户选中的事实。分类、引用校验、解析输出分别限制为 256、512、4096 Token；主回答沿用 800—6000 Token 的分档限制。
- 阶段入口、出口、网络发起和响应分块读取检查截止时间。慢速响应体不能靠持续传输绕过读取预算。该控制是协作式截止检查，不能强制中断已阻塞的系统 DNS、数据库操作或本地 CPU 工作，也不承诺客户端取消后供应商停止计费。
- 预算不改变资料适用范围、手动选卡与隐藏记忆规则。耗尽后不再发起模型调用，不将失败输出当作可保存建议。

### 执行记录

- SQLite 增量创建 `harness_runs` 表及账号/时间索引，不修改已有记忆列或内容。记录请求 ID、账号、流程版本、非密钥配置指纹、模式、阶段耗时、调用与重试、降级及过滤类别、可见候选/引用 ID、实际用量。阶段嵌套时耗时不可简单相加，总耗时单独记录。
- 每组可见候选 ID 最多记录 200 个，并记录总数；隐藏候选只记数量，不记 ID、标题或正文。过滤原因目前按范围/限定选卡、相关性/去重、重排门槛、数量上限及明确替代分类，不提供逐条自然语言解释。
- 不保存用户提问、模型正文、原始供应商错误、请求头或 API Key。供应商未返回有效用量、网络失败或响应解析失败时，用量标记未知；全部调用都有有效 `total_tokens` 才返回整轮合计，不能用估算冒充实际计费。
- 每个账号在写入执行记录时清理超过 **7 天**的历史，并仅保留最新 **1000 条**。清理是该账号下一次请求触发，不是后台定时清理；不删除其他账号记录。
- 仅本地持久化，不新增用户调试面板或云端上报。开发排障按账号及请求 ID 查询 `harness_runs`；响应只增加安全摘要 `meta.harness`。记录失败时 `trace_persisted=false`，业务成功结果保留。
- 健康检查返回 `harness_version: "1"`，可区分新旧运行服务。源码更新和前端构建不等于桌面安装包已更新；启动服务时应用增量表结构。

验证：`python3.12 -m unittest discover -s evals -p 'test_*.py'`，其中 `evals.test_harness` 覆盖执行契约、预算、记录、隔离及失败路径。真实模型收益对照仍按 PRD H05 单独执行。

## 核心模块设计

### 1. 用户可见记忆卡模块

- 只保存用户手动添加、手动保存、手动修改过的记忆卡。
- 支持查看、编辑、删除、搜索、手动指定调用。
- 是用户真正感知和管理的“显式记忆资产”。

### 2. 系统后台记忆模块

- 系统从对话、处理中自动抽取隐式记忆。
- 默认不直接展示给用户，不进入用户可管理列表。
- 主要用于提升自动召回质量和建议上下文完整性。

### 3. 检索召回模块

- BM25 关键词召回负责命中显式关键词、项目、客户、需求和事实线索。
- 向量检索在 embedding 配置可用时负责补充语义相似内容。
- 规则过滤负责屏蔽严格指定外的自动补卡、截至日期之后的卡、强事实类型不匹配卡、跨项目误召回和跨账号候选。
- 重排模块负责筛出真正进入本轮回答的 Top 3-5 张记忆。
- 2026-10-19：已收紧查询扩展和关键词入选条件，并为通用召回增加模型重排低分拒收；新增精确结果集和无相关资料回归。下一步用真实中文模型与独立业务样本校准阈值，详见 SPEC「召回精度优化」。

### 4. 账号数据隔离模块

- 用户可见记忆卡、系统后台记忆、聊天记录和会话上下文必须按账号隔离读取和写入。
- 登录、退出或切换账号后，当前对话区不得继续展示上一账号聊天记录。
- 模型配置数据不纳入账号隔离范围，默认保留本机已有 API Key、模型选择和基础参数。

### 5. 权重治理模块

- 不要求用户维护复杂状态。
- 系统后台根据以下信号动态调整记忆权重：
  - 当前问题相关度
  - 新鲜度
  - 历史使用价值
  - 是否被新内容覆盖
  - 来源权重（用户可见记忆卡高于后台隐式记忆）

### 6. 建议生成模块

- 输出建议摘要、详细建议、判断依据、下一步动作、不确定信息。
- 回答必须带引用来源。
- 没有依据支持的内容不得伪装成确定性结论。

## 关键实验（写进 DECISIONS 的证据）

1. 同一组工作问题做三组对照：
   - 方案 A：无记忆参与，直接对话
   - 方案 B：仅 BM25 关键词召回
   - 方案 C：BM25 关键词召回 + 向量检索 + 重排
   对比建议质量、引用准确性、用户主观可用性。

2. 对照“只用用户可见记忆卡”与“用户可见记忆卡 + 后台隐式记忆”：
   - 看是否能提升召回覆盖率
   - 看是否会增加误召回
   用数据判断后台隐式记忆是否值得保留。

3. 对照“无权重治理”与“带权重治理”：
   - 看新旧记忆冲突场景下，建议是否更稳定
   - 看陈旧记忆误命中率是否下降

## 备选方案（已否）

- **GraphRAG / 图数据库路线**：当前阶段记忆关系规模和问题复杂度不够，投入过重，暂不采用。
- **Agentic RAG**：动态编排复杂、延迟高、可观测性差，1.0 不需要。
- **全部记忆直接塞入长上下文**：成本高、污染上下文、难做来源控制与权重治理。
- **只做用户可见记忆卡，不做后台隐式记忆**：可作为最小备份方案，但会损失自动召回覆盖率，不作为当前主方案。
